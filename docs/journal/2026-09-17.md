## 1. Feature 003 — Order lifecycle visibility (PR #3, merged)

**Problem**: every order in the database read `Submitted`, including the eleven that had completed.
The saga finished, Payment recorded `Approved`, Inventory deducted the stock — and the `orders` row
was never told. `OrdersController` had only `POST`, so nothing could have shown otherwise.

**Built**: `OrderCompletedConsumer` and `OrderFailedConsumer` (the service's first consumers ever),
plus `GET /api/orders` and `GET /api/orders/{id}`, scoped by `ICurrentUser`.

**Decisions worth keeping**:

- Idempotency is a **guarded transition**, not configuration:
  `UPDATE orders SET ... WHERE "Id" = @id AND "Status" = 'Submitted'`. A redelivery affects zero
  rows. Loading the order and testing its status first is the obvious shape and is wrong — two
  concurrent deliveries both read `Submitted` and both write.
- Another shopper's order answers **404, not 403**. The owner is in the `WHERE` clause, so the
  handler never holds somebody else's order. A 403 would confirm the id is real.
- Four `OrderStatus` values stay unreachable by design. `Pending` turned out to be one of them —
  `SubmitOrderCommandHandler` overwrites the entity initialiser before the row is saved — which the
  issue had not noticed.

### The defect this feature nearly shipped

The first end-to-end run settled the order correctly **and left its two units held**. Cause:

```
$ docker exec e-commerce-rabbitmq rabbitmqctl list_queues name messages consumers
OrderCompleted	0	2        <- two services, one queue
```

MassTransit derives a queue name from the **consumer class name**. Inventory already had a class
called `OrderCompletedConsumer`; adding one with the same name in Order made both services bind to
the same queue and *compete* for it. Publish/subscribe fans out per **endpoint**, not per service.
Roughly half of all orders would have settled without their stock ever being confirmed.

**All fifteen unit tests were green while that bug was live.** The in-memory test harness has no
queue names to collide. Fixed with an endpoint-name prefix; now recorded in `CLAUDE.md`.

## 3. Feature 004 — One source of truth for stock (PR #5, merged)

**Problem** (filed as #4): Catalog held `Product.StockQuantity`, assigned once at creation and never
written again — no update command, no consumers, so the number could not change. `GET /api/products`
is `[AllowAnonymous]`, so that was what an anonymous shopper read while deciding whether to buy. One
product read **50** in the catalogue while Inventory went from 10 to 8.

**Built**: Inventory announces availability; Catalog keeps a read model and reports
`"InStock"` / `"OutOfStock"`. No count leaves Catalog at any level of detail.

### The mutation check that justified the design

Redelivery and reordering *look* like one requirement and are two. Proven by removing each guard
separately:

| Guard | 10× delivery test | Older-arrives-later test |
| :--- | :--- | :--- |
| None | ❌ fail | ❌ fail |
| Naive `p.Availability != isAvailable` | ✅ **passes** | ❌ fail |
| Shipped (compares `ObservedAt`) | ✅ | ✅ |

The middle row is the whole argument. The obvious guard — *write only when the value differs* —
survives a duplicate and therefore **looks sufficient**, while letting an older announcement
overtaken in flight overwrite a newer one. That is the expensive direction: the listing offers goods
that are gone. One mutation would not have shown it.

### Correction posted to issue #4

The issue claimed *"neither document mentions it"*. That was wrong —
`docs/architecture/microservices-design.md` had a whole section calling `StockQuantity`
"descriptive only" and stating that "nothing may read it for an availability decision". The
duplication was **known**, and leaving it was deliberate.

It does not change the finding — the field was on a public endpoint, and a shopper deciding whether
to buy is making exactly that decision — but "nobody noticed" and "somebody decided otherwise" are
different things. The doc is rewritten, and the lesson it now carries is the general one:
**"nothing may read this" is a wish, not a constraint.** A duplicated value that is reachable will
be read.

**Six publish sites** now announce stock movement — reserve, release, confirm, expire, set-on-hand,
register. Six chances to forget one, and a forgotten one is invisible. `AnnouncementTests` has one
test per site; an EF `SaveChanges` interceptor would have made the omission impossible and was
rejected as unverified.

## 5. Feature 005 — Containers (PR #10, open)

**Built**: one Dockerfile for all seven services, a compose overlay that brings the whole system up,
configuration from the environment, and a CI job that asserts no image layer carries a credential.
`start-dev.sh` is untouched. Details in
[running-in-containers.md](../infrastructure/running-in-containers.md).

### The verification script gave a false pass

The first version did `docker save | tar -t | grep`. It reported clean on the real image. Then an
image that provably contained a secret — `COPY .env` then `RUN rm`, the exact case the script exists
to catch — was also reported clean.

`docker save` emits an OCI layout: `blobs/sha256/<digest>`, every layer **gzipped**. Listing the
outer tar shows digest names and never a file path; grepping it sees compressed bytes. It was
scanning the wrong level of nesting and **could not have failed on anything.**

It now decompresses every blob, reads the tar inside, and reports how many filesystem layers it
actually read — reading zero is a failure, because a check that inspects nothing is not a clean
image.

### Four plan assumptions that were wrong

Each found by running it, not by reading:

1. **The YARP environment-variable override does not bind.** The variable is present in the
   container and YARP still dials `localhost:5057`. `Logging__LogLevel__Default=Warning` takes
   effect on the same container, so the provider works; the colon form failed too; command-line
   arguments work. **Cause not established, and said so** rather than guessed.
2. **The infrastructure containers had no health checks**, though the task said to use "the ones
   they already define".
3. **`aspnet:10.0` ships neither `curl` nor `wget`**, and a container health check must run inside
   the container.
4. **`*_DB_PORT` is 5432 inside the container network** — the 5433–5438 are host publications.

### And one mistake of my own

Orders failed for no visible reason and the containers took the blame for a while. A leftover
`dotnet run` from an earlier test was holding port 5061 with `PAYMENT_OUTCOME=Reject`, shadowing the
Payment container. The earlier kill command had been chained with `;` and failed silently.

`CLAUDE.md` **already documented** this trap. It happened anyway. That is why the end-to-end
scenario asserts `0` host processes rather than "it seems to work" — the assertion is the difference
between testing the containers and testing the host.

### Missed

**SC-004: the first build took 7m03s against a 5-minute budget.** The second took 24s, so the layer
ordering is doing its job — the cold build on that machine is simply slower than the spec assumed.
Recorded rather than quietly re-scoped.

## 6. What is still not true

Worth reading before planning tomorrow.

- **Nothing in CI runs more than one service at a time.** `auth-smoke` starts Identity, Catalog and
  Order; nothing runs the compose stack, Inventory, Payment or the Orchestrator together against a
  real broker. Both defects above that reached a running system — the queue collision and the
  shadowed port — are exactly the class that only appears when everything runs at once. This is the
  roadmap's Phase 7.
- **One Payment test failed once** during feature 003's full-solution run and did not reproduce in
  three subsequent runs. Which test was not captured. Not fixed — unexplained.
- **The payment gateway still moves no money.** `Provider = "Stub"`, a startup warning, and
  `/health` reporting `configuredOutcome` are the three signals that must survive any refactor.
- **Existing `Submitted` orders stay `Submitted`.** Their saga instances were finalized and removed,
  so a backfill would be inventing outcomes.
- **The whole catalogue reads `OutOfStock`** until Inventory announces each product. Expected:
  Catalog genuinely does not know, and cannot read Inventory's database to find out.
