# Authentication & User Database Design

This document details the database schema and implementation approach for User Authentication (Registration & Login) in the E-commerce system, following the principles of Clean Architecture.

---

## 1. Architectural Approach

In Clean Architecture, we decouple our Domain models from the database provider. The Authentication flow is divided across the layers:

```
  ┌──────────────────────────────────────────────────────────┐
  │ 1. WebApi (Presentation)                                 │
  │    - AuthController (/register, /register-seller,        │
  │      /login, /refresh, /logout)                          │
  │    - UsersController, ShopApplicationsController,        │
  │      SellersController, AddressesController              │
  │    - JWT Middleware & Token Validation                   │
  └─────────────┬────────────────────────────────────────────┘
                │
                ▼
  ┌──────────────────────────────────────────────────────────┐
  │ 2. Application                                           │
  │    - Commands: RegisterCommand, RegisterSellerCommand,   │
  │      LoginCommand, RefreshTokenCommand, LogoutCommand,   │
  │      Grant/Revoke role, Lock/Unlock, Ban/LiftBan,        │
  │      ApplyForShop, Approve/Reject shop application       │
  │    - Interfaces: IUserRepository, IRoleRepository,       │
  │      IShopApplicationRepository, IJwtTokenGenerator      │
  └─────────────┬────────────────────────────────────────────┘
                │
                ▼
  ┌──────────────────────────────────────────────────────────┐
  │ 3. Domain                                                │
  │    - Entities: User, Role, RefreshToken, SellerProfile,  │
  │      ShopApplication, DeliveryAddress                    │
  └─────────────▲────────────────────────────────────────────┘
                │ (Implements)
  ┌─────────────┴────────────────────────────────────────────┐
  │ 4. Infrastructure                                        │
  │    - EF Core Database Context (ApplicationDbContext)     │
  │    - Repositories (User, Role, ShopApplication, Address) │
  │    - JWT Token Generator service implementation          │
  └──────────────────────────────────────────────────────────┘
```

## 2. PostgreSQL Schema Design

Below is the SQL DDL representation of the Authentication tables. We use `UUID` for primary keys for security and distribution, and `TIMESTAMPTZ` for timezone-aware timestamps.

> **This is the logical design; the migrations are the source of truth**
> ([`Migrations/`](../../../server/src/Services/Identity/Ecommerce.Identity.Infrastructure/Migrations/):
> `InitialCreate`, `CaseInsensitiveEmail`, `AddSellerProfilesAndOutbox`, `AddAccountLocks`,
> `AddShopApplications`; `AddDeliveryAddresses` adds the address book, which is not part of
> authentication). The generated [data model](../../reference/data-model.md#identity---ecommerce_identity_db-8-tables)
> lists every column as the migrations produce it. The tables and columns match, with three differences
> worth knowing before you query the database:
> - **Column names are PascalCase** — EF Core's default. It is `"Email"`, quoted, not `email`.
>   Only the table names are snake_case.
> - **Ids are generated by the application, not by `uuid_generate_v4()`**, and the `uuid-ossp`
>   extension is not installed. `IsActive` is the only column with a database default.
> - **Not every id is UUID v7.** Seeded roles and the bootstrapped admin use `Guid.CreateVersion7()`;
>   a self-registered user's id is left empty and filled by EF Core, which does not produce v7.

```sql
-- Enable UUID extension
CREATE EXTENSION IF NOT EXISTS "uuid-ossp";

-- 1. Roles Table
CREATE TABLE roles (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    name VARCHAR(50) UNIQUE NOT NULL,
    description VARCHAR(255)
);

-- 2. Users Table
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    email VARCHAR(255) UNIQUE NOT NULL,
    password_hash VARCHAR(255) NOT NULL,
    first_name VARCHAR(100) NOT NULL,
    last_name VARCHAR(100) NOT NULL,
    phone_number VARCHAR(20),
    is_active BOOLEAN NOT NULL DEFAULT TRUE,
    locked_until TIMESTAMPTZ,          -- a lock (specs/043); in the past means not locked
    lock_reason VARCHAR(500),
    banned_at TIMESTAMPTZ,             -- a ban (specs/043); set means banned, until lifted
    ban_reason VARCHAR(500),
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);

-- One account per mailbox whatever the case (#49). Beside the case-sensitive unique index.
CREATE UNIQUE INDEX "IX_users_Email_lower" ON users (lower(email));

-- 3. User Roles Junction Table (Many-to-Many)
CREATE TABLE user_roles (
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id UUID NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    PRIMARY KEY (user_id, role_id)
);

-- 4. Refresh Tokens Table (One-to-Many with User)
CREATE TABLE refresh_tokens (
    id UUID PRIMARY KEY DEFAULT uuid_generate_v4(),
    token VARCHAR(500) UNIQUE NOT NULL,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    expires_at TIMESTAMPTZ NOT NULL,
    revoked_at TIMESTAMPTZ,
    replaced_by_token TEXT
);

-- 5. Seller Profiles (One-to-One with User) - the shop behind a seller's account (specs/027)
CREATE TABLE seller_profiles (
    user_id UUID PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,  -- one shop per account
    shop_name VARCHAR(100) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL,
    updated_at TIMESTAMPTZ NOT NULL
);

-- 6. Shop Applications (One-to-Many with User) - asking to sell (specs/044)
CREATE TABLE shop_applications (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    shop_name VARCHAR(100) NOT NULL,
    description VARCHAR(1000),
    phone VARCHAR(20),
    status VARCHAR(20) NOT NULL,       -- 'Pending' | 'Approved' | 'Rejected'
    decision_reason VARCHAR(500),
    decided_by UUID,
    decided_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ NOT NULL
);

-- At most one pending application per person, whatever raced.
CREATE UNIQUE INDEX "IX_shop_applications_one_pending"
    ON shop_applications (user_id) WHERE status = 'Pending';
-- The queue: pending, oldest first.
CREATE INDEX ON shop_applications (status, created_at);

-- Emails any service asked Identity to send (specs/060), kept until sent - see features/email.md.
CREATE TABLE outgoing_emails (
    id UUID PRIMARY KEY,                 -- the requester's id: a redelivery inserts nothing
    recipient_id UUID NOT NULL,
    template VARCHAR(64) NOT NULL,
    data_json JSONB NOT NULL,
    language VARCHAR(10) NOT NULL,
    status VARCHAR(20) NOT NULL,         -- Pending / Sent / Failed
    attempts INT NOT NULL,
    next_attempt_at TIMESTAMPTZ NOT NULL,
    sent_at TIMESTAMPTZ,
    last_error VARCHAR(1000),
    created_at TIMESTAMPTZ NOT NULL
);
CREATE INDEX "IX_outgoing_emails_due" ON outgoing_emails (next_attempt_at) WHERE status = 'Pending';

-- Indexes for performance on query patterns
CREATE INDEX idx_users_email ON users(email);
CREATE INDEX idx_refresh_tokens_token ON refresh_tokens(token);
```

## 3. Data Dictionary

### `users` Table
| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `id` | UUID | PK, Default Gen | Unique identifier of the user |
| `email` | VARCHAR(255) | Unique, Unique on `lower(email)`, Not Null | User's email address (used as login username). Stored as typed; every lookup goes through `EmailKey.For` (trim, lower-case), so `A@x.com` and `a@x.com` are one account (#49) |
| `email_confirmed_at` | TIMESTAMPTZ | Nullable | When the link sent to the address was used (specs/063). Null: not confirmed - the account buys but opens no shop. Accounts from before specs/063 were set to their `created_at` |
| `password_hash` | VARCHAR(255) | Not Null | BCrypt hash (`BCrypt.Net-Next`) |
| `first_name` | VARCHAR(100) | Not Null | User's first name. Also the token's `given_name` claim, which signs the person's product reviews |
| `last_name` | VARCHAR(100) | Not Null | User's last name - never put in a token |
| `phone_number` | VARCHAR(20) | Nullable | Not set by any current endpoint |
| `is_active` | BOOLEAN | Default True | Exists in the schema, but **no code reads it**. Stopping an account uses the lock and ban columns below |
| `locked_until` | TIMESTAMPTZ | Nullable | A lock set by staff (specs/043). Locked while it is in the future; a lock that has run out needs no clean-up |
| `lock_reason` | VARCHAR(500) | Nullable | Why - shown to the person after the right password |
| `banned_at` | TIMESTAMPTZ | Nullable | A ban set by an administrator (specs/043). Banned while set; no end date |
| `ban_reason` | VARCHAR(500) | Nullable | Why - shown to the person after the right password |
| `created_at` | TIMESTAMPTZ | Default Now | Account creation timestamp |
| `updated_at` | TIMESTAMPTZ | Default Now | Last account update timestamp |

A lock and a ban are two nullable pairs rather than one status column: they can overlap, and an
earlier image of the service must still read the row (the migration only adds columns).

### `refresh_tokens` Table
| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `id` | UUID | PK, Default Gen | Unique identifier of the token |
| `token` | VARCHAR(500) | Unique, Not Null, Index | Cryptographically secure random token string |
| `user_id` | UUID | FK -> `users(id)`, Cascade | Owner of the refresh token |
| `expires_at` | TIMESTAMPTZ | Not Null | Token expiration timestamp |
| `revoked_at` | TIMESTAMPTZ | Nullable | Timestamp when token was revoked |
| `replaced_by_token`| TEXT | Nullable | Token that replaced this token (for rotation). Null when the token was revoked by a detected reuse or by a lock or ban |

A rotated or revoked token that has not expired is kept, because it is what recognises a stolen token
coming back (see [security best practices §4.2](./security-best-practices.md)). Signing out deletes
the token's row.

### `password_reset_tokens` Table
| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `id` | UUID | PK, generated by the application (v7) | |
| `user_id` | UUID | FK -> `users(id)`, Cascade, Index | Whose password the link resets |
| `token_hash` | CHAR(64) | Unique, Not Null | Hex SHA-256 of the token in the link. **The token itself is never stored** |
| `expires_at` | TIMESTAMPTZ | Not Null | 30 minutes after it was asked for |
| `used_at` | TIMESTAMPTZ | Nullable | Set by the one guarded `UPDATE` that uses the link |
| `created_at` | TIMESTAMPTZ | Not Null | |

Asking again deletes the person's unused rows first, so only the newest link works (specs/061). A used
row stays as the record that the link was used. Since specs/062 a link asked for within a minute of the
last one sends nothing.

### `email_confirmation_tokens` Table
The same shape as `password_reset_tokens` (specs/063): `id`, `user_id` (FK, cascade), `token_hash` CHAR(64)
unique - **the token itself is never stored** - `expires_at` (24 hours), `used_at` (set by the one guarded
statement that uses it) and `created_at`. Sending a new link deletes the person's unused ones first, and at
most one is sent a minute.

### `sign_in_throttles` Table
| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `email_key` | VARCHAR(255) | PK | The email as sign-in compares it: trimmed, lower-case. **Not** a user id - unknown addresses are counted too (#28) |
| `failures` | INTEGER | Not Null | Wrong passwords in the current window; back to 0 when a pause starts |
| `window_started_at` | TIMESTAMPTZ | Not Null | 15 minutes after this, the count starts again |
| `blocked_until` | TIMESTAMPTZ | Nullable | Every sign-in for this email is 429 until then |

Changed only by single atomic statements (specs/062); cleared by the right password or a reset; purged
hourly once nothing runs.

### `seller_profiles` Table
| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `user_id` | UUID | PK **and** FK -> `users(id)`, Cascade | The seller's account. Being the key makes "one shop per account" a constraint |
| `shop_name` | VARCHAR(100) | Not Null | The name shoppers see under every product. Catalog keeps a copy as a read model, fed by `SellerRegisteredEvent` / `SellerRenamedEvent` |
| `created_at`, `updated_at` | TIMESTAMPTZ | Not Null | |

Written when a shop application is **approved**, in the same transaction as the `Seller` role and the
`SellerRegisteredEvent` outbox row.

### `shop_applications` Table
| Column | Type | Constraints | Description |
| :--- | :--- | :--- | :--- |
| `id` | UUID | PK, generated by the application (v7) | |
| `user_id` | UUID | FK -> `users(id)`, Cascade | The applicant, from the token |
| `shop_name` | VARCHAR(100) | Not Null | |
| `description` | VARCHAR(1000) | Nullable | What they mean to sell - what staff decide on |
| `phone` | VARCHAR(20) | Nullable | |
| `status` | VARCHAR(20) | Not Null | `Pending`, `Approved` or `Rejected`, stored as text |
| `decision_reason` | VARCHAR(500) | Nullable | Required for a rejection; the applicant reads it |
| `decided_by` | UUID | Nullable | The staff member, from their token |
| `decided_at` | TIMESTAMPTZ | Nullable | |
| `created_at` | TIMESTAMPTZ | Not Null | Queue order |

`IX_shop_applications_one_pending` is a **partial unique index** on `user_id WHERE status = 'Pending'`:
two tabs applying at once cannot queue the same person twice. A decision is one guarded
`UPDATE ... WHERE "Status" = 'Pending'`, so a second approval changes no row and is refused with 409. A
rejected application stays as history and the person may apply again. Shops that existed before
applications were introduced have no row and need none.

## 4. Seeded Data & Administrator Bootstrap

An empty database is brought to a usable state on Identity startup by
[`DataInitializer`](../../../server/src/Services/Identity/Ecommerce.Identity.Infrastructure/Persistence/DataInitializer.cs).
Every step is skipped once its data exists, so it is safe to run on each boot.

### Roles

| Role | Granted by | Purpose |
| :--- | :--- | :--- |
| `Admin` | The bootstrap step below - and nothing else | Full administrative access |
| `Customer` | Automatically, on registration (`register` and `register-seller`) | Default shopper role |
| `Seller` | Approval of a shop application by a moderator or an administrator | Lists and manages their own products; always held **with** `Customer` |
| `Moderator` | An administrator, through `PUT /api/users/{id}/roles/Moderator` | Staff: reviews shops, products and reviews, and may lock an account for up to 30 days |

The names and descriptions live in `RoleNames.Descriptions`; `DataInitializer` inserts any that are
missing, so a new role reaches an existing database at the next startup. When `RUN_MIGRATIONS_ON_STARTUP=true`
(containers), migrations are applied before seeding, so a fresh container starts.

Ids are generated at runtime with `Guid.CreateVersion7()` per
[ADR-001](../../architecture/adr-001-uuidv7-primary-keys.md), so they differ per environment. That
rules out EF Core's `HasData` seeding, which requires fixed primary keys baked into the migration.

### Bootstrapping the first administrator

Roles are part of the schema, so they are seeded in code. The first administrator is *operational
data* with a credential, so it comes from the environment and never from source control:

```bash
# server/.env
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=at_least_8_characters
```

The logic, in order:

1. **If any user already holds `Admin`, stop.** The bootstrap path closes permanently after the
   first administrator, so it can never be used to escalate privileges later.
2. If `ADMIN_EMAIL` / `ADMIN_PASSWORD` are unset, log a warning and skip — startup does not fail.
3. If the password is shorter than 8 characters, refuse rather than create a weak administrator.
4. If an account with that email already exists, **promote** it and leave its password untouched.
   Otherwise create a new one.

Registration always yields `Customer`, including `register-seller`, which adds a pending shop
application and no other role. `Admin` is only ever granted by this initializer: the API can grant and
revoke `Moderator` and nothing else, and `Seller` comes only from an approved application.

> Because roles are carried inside the access token, a newly granted or revoked role does not take
> effect until the holder's session is refreshed; the access token already issued keeps its roles
> until it expires (15 minutes).

## 6. Security & Flow Checklist

- [x] **Password Hashing**: Never store plain passwords. Use **BCrypt.Net-Next** in the Application/Infrastructure layer.
- [x] **JWT Tokens**: Issue short-lived Access Tokens (15 minutes) containing Claims (`sub`, `email`, `given_name`, `jti`, one `role` per role).
- [x] **Refresh Tokens**: Issue long-lived Refresh Tokens (e.g., 7 days) stored securely in HttpOnly cookies, and rotate them on use to prevent replay attacks.
- [x] **Email Uniqueness**: enforced by the database - case-insensitively, through `IX_users_Email_lower` (#49) - and an existing email is a **409** from the application check (#28). Two registrations of the same email at the same instant can still reach the unique index and surface as 500 — rare, and recorded rather than handled.
- [x] **Stopping an account**: a lock or ban refuses sign-in (403 with the reason, only after the right password), revokes every refresh token, and makes refresh answer 401. The access token already issued is refused within seconds by every service (specs/065, #112).
- [x] **One shop per account, one pending application per person**: the `seller_profiles` key and a partial unique index.
