# Phase 1 Data Model: Run the System in Containers

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-17

**No entity, no table, no migration.** This feature changes where the services run, not what they
store. Every database keeps its name, its port and its schema.

That is worth stating explicitly rather than omitting the document, because "containerisation" and
"database change" arrive together often enough that a reviewer will look for one.

The three things this feature does model are described in the spec's Key Entities. Their real shape
lives in [contracts/configuration.md](./contracts/configuration.md); what follows is only their
lifecycle and the rules that bind them.

---

## Service package

One runnable, self-contained copy of one service.

| Property | Rule |
| :--- | :--- |
| Contents | The published output of exactly one WebApi project, and the runtime it needs |
| Settings | **None.** It is told everything at start (FR-007) |
| Secrets | **None, in any layer** (FR-006) — not merely in the final one |
| Identity | One per service; seven in total |
| Privilege | No more than it needs (FR-013) |

**Lifecycle**: built → run, many times, in many places, unchanged. The same package is what runs
everywhere; only what it is told differs. A package that has to be rebuilt for a second environment
is not one of these.

---

## Environment settings

What makes one running copy different from another.

**Precedence, which this feature changes:**

```text
environment variable  >  .env file  >  appsettings.json  >  hardcoded default
```

Today the first two are reversed — the file calls `Environment.SetEnvironmentVariable`
unconditionally and wins. That inversion is what makes a package uncontainerisable: settings injected
at runtime would be overridden by a file inside it.

| Rule | Requirement |
| :--- | :--- |
| A missing required setting | Fails at startup, naming it (FR-010) |
| A setting absent from the environment | Falls back, ending at today's local value (FR-001, FR-002) |
| Two packages, different settings | Behave differently, from the same bytes (SC-002) |

## Exclusion list

What the build must never copy into a package.

**It is not the version-control exclusion list**, and the two are not interchangeable — that is the
whole finding behind [#7](https://github.com/jessiicamaru/e-commerce-asp-dotnet-practice/issues/7).
`server/.env` is correctly excluded from version control and would be copied into a package anyway,
because the build tool reads a different file.

| Must exclude | Why |
| :--- | :--- |
| `**/.env*` | Real `JWT_SECRET`, `DB_PASSWORD`, `ADMIN_PASSWORD` |
| `**/bin/`, `**/obj/` | Host build output; wrong architecture, and large |
| `.git/` | History, including every secret ever committed anywhere |
| `**/TestResults/` | Noise |
| `specs/`, `docs/` | Not needed at runtime |

**Ordering rule**: this list exists **before** the first build definition. Written afterwards, it
arrives after the moment it was needed — an image built once may have been shared, and a distributed
credential must be rotated rather than deleted.

## What does not change

- Six databases: `ecommerce_identity_db` (5435), `ecommerce_catalog_db` (5433),
  `ecommerce_order_db` (5434), `ecommerce_saga_db` (5436), `ecommerce_inventory_db` (5437),
  `ecommerce_payment_db` (5438). Same names, same host ports, same volumes.
- Every migration already applied. **No new migration is generated by this feature.**
- Every service's HTTP port as seen from the host: 5000, 5056–5061.

## One change of mechanism, not of data

Nothing creates the schema today except `start-dev.sh` calling `dotnet ef database update` six times —
verified, not assumed:

```bash
$ grep -rn "Database.Migrate()" server/src --include=*.cs | grep -v obj
# no matches
```

A runtime image has neither the SDK nor the source, so that route does not exist inside a container.
Services gain the ability to apply their own migrations, **off unless `RUN_MIGRATIONS_ON_STARTUP` is
`true`** (research D3). The schema produced is identical either way; only who applies it changes.
